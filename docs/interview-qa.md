## 2. 项目 1:AI 图像与人像生成平台

### 2.1 业务背景与客户需求

#### Q: 这个项目到底在卖什么能力?客户要的是什么?

**A**: 卖的是**"可控、稳定、能批量交付"**的图像 / 人像生成与编辑能力。
典型场景:文生图、图生图、局部编辑(inpainting)、一键证件照 / 头像生成与背景替换。
客户要的是:结果一致、失败少、并发扛得住、接口好接。

#### Q: 业务逻辑链路从输入到输出怎么走?你能按步骤讲清楚吗?

**A**: 我把它拆成一条流水线:

1. **输入**:prompt/negative prompt、参考图(可选)、mask(可选)。输出规格:尺寸、背景、张数、格式等。
2. **入口校验**:图片格式 / 尺寸、mask 对齐、参数范围(避免把系统打爆)。
3. **前处理**:证件照场景先做人像分割抠图(U²-Net 或 SAM),得到前景 mask/alpha。
4. **生成 / 编辑**:按需求走文生图、图生图或 inpainting。
5. **可控增强**:结构要稳时挂 ControlNet;风格 / 一致性要稳时挂 LoRA。
6. **后处理**:裁剪对齐、背景模板合成、压缩与格式导出。
7. **交付与回溯**:结果落盘 / 对象存储,记录参数与日志,保证可复现。

### 2.2 数据与工程输入输出

#### Q: 你处理的数据是什么?有没有敏感 / 合规风险?

**A**: 数据主要是用户上传的人像图 / 参考图、局部编辑 mask,以及文本提示词。
合规上我会强调两点:
- 只保存业务必要数据(或按公司策略脱敏 / 限时保留)
- 记录访问与导出日志,避免滥用

#### Q: 输出如何保证可复现?如果客户说"昨天那张很好,今天要同款"怎么办?

**A**: 我会保存"可复现三件套":输入素材索引(图 / mask)、关键参数(分辨率、steps/sampler、CFG、ControlNet/LoRA 权重等)、以及 seed 策略。

### 2.3 核心算法与原理(面试够用)

#### Q: 你们主模型是什么?用在什么位置?

**A**: 主模型是 **Stable Diffusion**: 文生图 / 图生图 / inpainting 都是它。
- 结构控制用 **ControlNet**
- 风格 / 一致性用 **LoRA**
- 人像抠图用 **U²-Net** 或 **SAM**

#### Q: Stable Diffusion 原理你怎么讲清楚?

**A**: 我会用"加噪-去噪"来讲:训练时把图像逐步加噪,模型学会在每个时间步预测噪声;推理时从噪声出发,UNet 逐步去噪得到图像。
- 文本提示通过 cross-attention 影响去噪方向
- **CFG** 是把有条件 / 无条件预测组合,**增强提示词控制**

#### Q: ControlNet 怎么能控结构?

**A**: 它把条件图(边缘 / 姿态 / 深度等)编码成特征,**注入到 UNet 的多层**;让去噪过程被结构条件约束。
- 业务价值:减少人脸姿态、身形变形,特别是"要像某张参考结构"的场景

#### Q: LoRA 为什么是工程上常用的微调方式?

**A**: LoRA 是**低秩适配**:冻结主模型权重,只学少量低秩增量参数(BA),**成本低、切换快、上线风险小**。
工程里它像插件:不同风格一套 LoRA,按业务需要动态加载。

### 2.4 推理服务工程化(我负责的核心部分)

#### Q: 整体架构你怎么搭?为什么是 FastAPI + 队列?

**A**: 我设计的是 **FastAPI + 队列的异步推理架构**:
- **API 层**:负责接入、校验、入队并返回 task_id
- **Worker 层**:负责模型预加载、推理与后处理
- **Redis / MySQL**:记录任务状态与结果索引
- 最终结果通过文件系统或对象存储交付
- **队列的价值是解耦入队与推理**:能并发、能重试、状态可查询,避免同步阻塞把接口打死

#### Q: 你具体做了哪些性能优化?为什么有效?

**A**: 我用的是一套工程组合:
- **FP16** 降显存与计算
- **合理 batch** 提升 GPU 利用率
- **模型权重预加载**避免重复加载
- **多进程 / 多模型实例**提升吞吐
- 同时配合**队列限流**,避免并发把 GPU 打满导致整体延迟飙升

#### Q: 你简历里写单张耗时 4.5s → 1.6-2.0s,这个指标怎么来的?

**A**: 面试时我会先把口径说清楚:
- 同一硬件、同一分辨率、同一 steps/sampler/CFG
- 说明是**端到端耗时**还是**纯推理耗时**
- 简略里我写了优化手段(FP16 / batch / 预加载 / 多实例),但**硬件与参数口径没展开**——面试前我会把这些补丁补充齐

#### Q: 稳定性 / 失败率你怎么降?怎么解释失败重试不是反复横跳?

**A**: 我做的是**"分层处理"**:
- **入口校验**:不合规参数直接拒绝,避免进入推理
- **超时**:推理与外部依赖都有超时
- **重试**:只对**可恢复错误**重试(网络 / 资源抖动等),对**参数错误不重试**
- **可解释错误码**:错误码 + 人都能看懂的提示

这种重试是"**有边界的**",不是无限重试把系统拖垮。

### 2.5 高频追问点(我会怎么答)

#### Q: 怎么保证证件照风格一致,不会一张一个样?

**A**: 我不靠 prompt 让模型"自己学一致",而是**靠模板化**:
- 分割加图锁定主体边界
- 背景模板锁定颜色与质感
- 裁剪规则锁定比例
- 参数锁定降低随机性
- 必要时 LoRA 固定风格、ControlNet 固定结构

#### Q: 生成质量怎么评估?你有什么客观指标吗?

**A**: 生成任务很难只用单一分数定胜负。
工程上我会蹭两层:
- **线上质量**:人工抽检 + 失败类型统计(跑偏、空图、构图错位等)
- **离线对比**:固定输入与参数组 A/B,关键场景做对比集

## 5. 项目 4:车险纯保费定价(Tweedie-GLM + IRLS)

### 5.1 业务问题

#### Q: 为什么车险纯保费要单独建模?

**A**: 车险有**两个特殊点**:
- **高零赔付率**:很多保单没有赔付
- **长尾赔付分布**:少数保单赔付金额巨大

传统正态回归 / 泊松回归都不好用。

### 5.2 模型与原理

#### Q: Tweedie 分布为什么适合?

**A**: Tweedie 分布在 **1<p<2** 时可视为**复合泊松-伽马**:
- 允许 0
- 对长尾友好

```
Var(Y) = φ · μ^p
```

#### Q: log 链接为什么好?

**A**: log 链接让:
```
η = X·β
μ = exp(η)
```

**关键意义**: `exp(β_k)` 是**乘性费率因子**,业务方可以直接解读为"特征 k 增加 1 个单位,赔付率变为原来的 N 倍"。

#### Q: IRLS 怎么训练?

**A**: 我会用一句话讲清:
- 加权最小二乘迭代,**权重根据当前 μ 与 Var(μ) 重新计算**
- 监控收敛(对数似然变化 < 阈值)

### 5.3 我的工作

#### Q: 你做了哪些事?具体到什么程度?

**A**: 我会落到三件事:
- **特征工程**:对驾驶行为、里程、时段、地区等特征分箱与筛选
- **特征选择**:**单变量分析 + 互信息**降低共线性
- **建模与解释**:Tweedie GLM(log 链接)训练,输出**可解释系数表**与费率因子影响分析

## 6. 项目 5:人脸识别轻量化升级(MobileNet + ArcFace)

### 6.1 业务问题

#### Q: 为什么从 MTCNN + 重模型迁移到 MobileNet + ArcFace?

**A**: 主要是**线上的瓶颈**:
- 老模型(MTCNN + 重 backbone)在 CPU 上推理慢
- 上线后端到端时延不达标

### 6.2 MTCNN 与对齐

#### Q: MTCNN 怎么对齐?

**A**: MTCNN 是三级网络(P-Net → R-Net → O-Net):
- 输出:边界框 + 5 个关键点(双眼 / 鼻 / 嘴角)
- 对齐后做仿射变换,**将人脸标准化到固定位置**
- **对齐稳定决定 embedding / 阈值稳定**

### 6.3 MobileNet 轻量化

#### Q: MobileNet 为什么能用?

**A**: 它用**深度可分离卷积**:显著降低计算与参数,**适合在线部署**。
对项目来说,主要是把"能跑"变成"扛得住"。

### 6.4 ArcFace Loss

#### Q: ArcFace 损失怎么写?

**A**:
```
L = -log( exp(s · cos(θ_y + m)) / (exp(s · cos(θ_y + m)) + Σ_{j≠y} exp(s · cos(θ_j))) )
```

**通俗解释**: 在角度空间上**给本类加一个 margin**,使同类更紧凑、异类更分散;比 Softmax 更适合人脸识别。

### 6.5 指标口径

#### Q: 怎么报告结果?

**A**: 我会先报**口径**:
- 训练数据规模(人脸 ID 数 / 总图片数)
- 评测集规模 + 评测指标(Top-1 / EER / ROC)
- 阈值设定

模型规模 / 蒸馏 / 是否多尺度也要点出来。

### 6.6 工程产出

#### Q: 你这个项目最终交付了什么?

**A**:
- 完整**训练脚本**与**部署说明**,支持后续在线服务接入
- 我做了:**样本清洗 + 难例挖掘 + 多阶段数据增强**(光照、遮挡、姿态)+ 调参与对比实验

## 7. 项目 6:多元数据融合货车智能调度 PoC(RL + ACO + 可视化平台)

### 7.1 业务定位

#### Q: 这个项目是 Demo 还是上线?

**A**: 这是 PoC:算法验证 + 调度平台最小可行版本。
平台前端支撑物流团队实时监控车辆轨迹、调度任务进度与风险事件。

### 7.2 算法框架(MDP + RL + ACO 混合)

#### Q: 你怎么定义 MDP?

**A**: 状态 S:车辆 / 订单 / 路网 / 约束信息。
动作 A:**派单 / 插单 / 重路由**(可用 action masking)。
回报 R:-(里程 + 延误 + 违约 + 风险成本);reward shaping 关键。

#### Q: 为什么不直接跑 RL?

**A**: RL 三个核心问题:
- **离线依赖仿真 / 回放环境**(直接在线探索成本高)
- **约束处理**:**动作掩码 + 软罚项 + 修复算子**
- **基线启发式兜底**:RL 做增益,启发式做保底

### 7.3 ACO 局部精炼

#### Q: ACO 怎么写?

**A**:
```
P(i→j) ∝ τ^α · η^β
τ_ij ← (1-ρ) · τ_ij + Σ_k Δτ^k_ij
```

它是 RL 给出的粗粒度方案做局部精炼。

### 7.4 可视化平台

#### Q: 你做可视化平台的核心考量是什么?

**A**: 可视化不仅是 UI,**更是解释与验收手段**:
- **地图叠加**:路线 / 时间窗 / 风险点
- **成本分解**:里程 / 延误 / 违约 / 风险各项占比
- **回放对比**:基线 vs 优化,用于上线验收

## 11. 项目 10:车货匹配算法(GeoHash + 多因子评分)

### 11.1 业务问题

#### Q: 车货匹配要解决什么?

**A**: 给定货物重量 + 起点终点经纬度,在候选货车集合中找出最优匹配车辆。
难点:**轨迹与订单路线是否匹配** + **车辆当前位置是否空闲**。

### 11.2 算法设计

#### Q: GeoHash 是怎么用的?

**A**: GeoHash 是空间地址编码,把经纬度编码成字符串:
- **5 位 GeoHash** ≈ 5km × 5km(配 8 邻域可达 14km)
- **4 位 GeoHash** ≈ 25km × 25km(配 8 邻域可达 65km)

我用 GeoHash 做**空间索引**,处理边界与偏移问题,支持**快速候选车辆召回**。

#### Q: 多因子评分怎么设计?

**A**: 设计多因子打分模型:
- 匹配度(起终点接近)
- 距离成本
- 空驶 / 空闲时间
- 历史履约表现

**加权归一化形成综合评分**。

### 11.3 工程细节

#### Q: 还有什么细节?

**A**: 还做了:
- **历史轨迹分段与清洗规则**(片内 < 1h、片间 ≥ 1h)
- **抽取常驻起讫点**与运行特征
- **边界与偏移问题**处理
